# opportunity routing checklist

Use this gate before creating a job board, lead board, community marketplace, internal automation queue, or software surface for paid/high-priority work.

## demand proof

- [ ] The requester, buyer, user, or accountable operator is named by role.
- [ ] The painful job is stated without tool jargon.
- [ ] The current cost is described as time, money, risk, delay, quality loss, or missed opportunity.
- [ ] There is evidence the problem already recurs or is urgent now.
- [ ] The acceptance test is concrete enough for a reviewer to accept or reject.

## capacity proof

- [ ] A capable operator role, team, or vendor role can deliver a first manual version.
- [ ] Reusable assets have been checked before starting from scratch.
- [ ] Source inputs and data boundaries are explicit.
- [ ] Authority, privacy, and review boundaries are explicit.
- [ ] The first attempt has a due artifact, not only a conversation.

## board/workbench proof

- [ ] Requests have visible states: raw, qualified, claimed, blocked, delivered, accepted, archived.
- [ ] Every claimed request links to a request slip or workbench folder.
- [ ] Delivered artifacts link to source inputs and checks.
- [ ] Acceptance/rejection reasons are recorded.
- [ ] Private customer, person, channel, deal, and financial details are excluded from any shared sanitized corpus.

## escalation proof

- [ ] The board has produced useful manual or semi-manual results before custom software is built.
- [ ] The repeated bottleneck is named: intake, matching, source prep, delivery, review, handoff, billing, or reporting.
- [ ] The next mechanism targets only that bottleneck.
- [ ] A template or checklist was considered before a script.
- [ ] A script or one-shot model call was considered before an agent.
- [ ] A product/platform build is justified by repeated demand, governance, sharing, scale, or economics.
